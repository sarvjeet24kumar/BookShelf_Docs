Auth Flow

BookShelf implements a multi-factor authentication system with OTP-based verification for both signup and login. All authentication flows are tenant-scoped using the Tenant-ID header.

Registration & Email Verification

Signup Flow

  1. User sends credentials to POST /api/v1/auth/signup/ with Tenant-ID header
  2. System validates:
  3. Tenant exists and is active
  4. Email unique within tenant
  5. Username globally unique
  6. Password meets strength requirements
  7. User created with is_email_verified=False, is_active=False
  8. 6-digit OTP generated, hashed, and cached in Redis
  9. Celery task dispatches verification email asynchronously
  10. Response: "Verification code sent to your email."

Email Verification

  1. User submits OTP to POST /api/v1/auth/verify-email/
  2. Can identify via email OR username
  3. Requires Tenant-ID header
  4. System validates OTP against cached hash
  5. On success:
  6. User marked is_email_verified=True, is_active=True
  7. OTP cache cleared
  8. Account now ready for login

Resend Verification OTP

  1. User requests new code via POST /api/v1/auth/resend-otp/
  2. Requires email OR username + Tenant-ID
  3. Previous OTP invalidated, new one generated
  4. Fresh 10-minute window starts

Login Flow (MFA with OTP)

Step 1: Credential Validation

  1. User sends credentials to POST /api/v1/auth/login/
  2. Accepts email OR username + password
  3. Tenant-ID optional (required for Admin/User, not for SuperAdmin)
  4. System validates:
  5. User exists in specified tenant
  6. Account not deleted (deleted_at is null)
  7. Email verified (is_email_verified=True)
  8. Account active (is_active=True)
  9. Password correct
  10. 6-digit OTP generated, hashed, cached (10min TTL)
  11. Celery task sends OTP via email
  12. Response: "OTP sent to your email. Please verify to complete login."

Step 2: OTP Verification

  1. User submits OTP to POST /api/v1/auth/verify-login/
  2. Requires email OR username + OTP
  3. System validates OTP (max 5 attempts per session)
  4. On success:
  5. OTP cache cleared
  6. JWT tokens issued
  7. Response contains both tokens for client storage

Password Management

Forgot Password

  1. User submits request to POST /api/v1/auth/forgot-password/
  2. Requires email OR username
  3. Tenant-ID optional
  4. System generates secure reset token
  5. Token cached in Redis, linked to user ID
  6. Celery task sends email with reset link
  7. Response always: "If an account exists, a reset link has been sent."
  8. Prevents email enumeration

Reset Password

GET Request (Load Form): 1. User clicks link to GET /api/v1/auth/reset-password/?token=<token> 2. System validates token exists and not expired 3. Renders HTML form for password entry

POST Request (Submit New Password): 1. User submits via form or API: - token, password, confirm_password 2. System validates: - Token valid and not expired - Passwords match - Password meets strength requirements 3. Updates user password (hashed) 4. Reset token cleared from cache 5. User can now login with new credentials

Change Password

  1. Authenticated user calls POST /api/v1/auth/change-password/
  2. Required fields:
  3. current_password: Must match existing
  4. new_password: Must meet requirements
  5. confirm_password: Must match new
  6. System verifies current password
  7. Updates to new password
  8. User must re-login on other devices

Authentication Middleware

TenantJWTAuthentication

Every protected request passes through:

  1. Extract JWT from Authorization: Bearer <token>
  2. Validate token signature and expiry
  3. Check access token JTI not in Redis blacklist
  4. Load user from token payload
  5. Verify user is active and not deleted
  6. Verify tenant is active (if applicable)
  7. Set request.user and tenant context
